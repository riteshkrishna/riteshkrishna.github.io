Automation of tasks and lowering of skill barriers are two primary usages of AI agents. In a cross-organization, cross-disciplinary collaboration, complimentary skills are required to act towards shared goals with speed, accountability, and desirably, through automated *workflows*. Here, a workflow can be understood as a sequence of tools that need to be executed in a certain order to produce a desired outcome. The output from one tool is consumed as the input for the subsequent tool, and so on. Agentic AI is quickly emerging as a technical paradigm to perform logical action sequences in automated fashion to replicate the manual process of building workflows. The business of building and executing workflows is as old as the computing itself, but the agentic paradigm and the related technologies offer something that was always desired, but was never truly there - the power to plan, co-ordinate, and execute multiple steps in a completely automated way. A central component of an agentic AI system is a LLM (Large Language Models) that handles the job of reasoning, co-ordination and execution of tools via the *agents*. 

## Motivation
A couple years ago, in the pre-LLM era, we wrote a [patent](https://patents.google.com/patent/US20220292389A1/en) about an intelligent compute workflow that could change its shape in the middle of an execution, depending on the nature of the data. We named this type of workflow as **Self-morphing workflows**. The basic idea was that there are set of pre-defined tools, where each tool had rich metadata associate with it. The metadata contained a variety of information related to the nature and usage of tool. There was also an ***orchestrator*** - a computationally adept engine that could read the tool-metadata, user instructions and the nature of data in flight. The orchestrator acted as the brain of the system, and depending on the nature of data, it would decide to call the appropriate tool in an ***event-driven manner***, eventually leading to creation of a workflow. The idea was theoretically simpler, but practically substantially harder to implement. The hardest part was the implementation of the orchestrator as its intelligence was limited to as much as we could explicitly state through instructions or inferences.

In the current LLM-era, the equivalent of _Orchestrator_ from our context, is a LLM model. Since a LLM model has a power to _think_, it makes the engineering effort to implement the orchestrator, almost obsolete. Instead of implementing orchestrator from scratch, one can just plug-and-play a LLM model in the original patent design and implement the whole system. 

Let me provide you an example as how LLM, combined with AI agents, can leverage what we know as ***the chain of thoughts*** technique to autonomously build a compute workflow comprising of multiple tools.


## A toy example of a workflow

I provide here a simple example from Life Sciences domain, but the task requirements are similar across other domains. Let's assume a scenario where a chemist and a biologist are working together to understand genetic triggers for a disease of interest. The have zoomed in on a gene/protein named BRCA1 and want to understand which other genes BRCA1 is known to interact with. The task requires searching through a publicly available knowledgebase and deriving a visual representation of interaction of BRCA1 with other known genes. Typically, a task like this requires some domain expertise in bioinformatics where one needs to understand the gene naming conventions, usage of knowledgebases, extraction of information etc. In this scenario, neither of the scientists may possess the bioinformatics skills and may reach out to their bioinformatics colleagues for help - or, in the world of *agentic systems*,  they may *prompt* the system to think, design and execute a workflow to give them the desired result. The agentic system would not have a hard-coded instruction to construct a workflow, but it could rather use the **chain of thoughts** technique to plan a workflow where at different stages, an agent (or a collection of them) would be called to perform particular operations. Each agent would be able to call a tool (or a set of tools) to perform specific set of actions. It is important to stress that the ***tools are the first-class citizens in the agentic world***, and define an agent's core capability.

The set of steps can be translated to a simple flowchart with four stages - understand which gene user is asking for, map the gene name to standard identifier, use the identifier to query a knowledgebase to extract the result in an image form, and do a final check before concluding.

One may also add an additional check in the beginning to make sure that the workflow is triggered only when the user provides a gene name, not just any random input. In this case, the flowchart will have decision step in the beginning that will decide if the workflow should be triggered or terminated straight away. The last three stages are specific operations and thus may have a tool for each of them. The schematic below shows the amended flowchart. <p style="color:red"> Different stages of the flowchart are coloured differently to denote specific operations. The last three stages of the flowchart have been numbered (coloured circles with numbers next to the blocks) - the circles denote the tool identifiers for the corresponding colour operation in the flowchart. </p>

The above flowchart shows an expert-curated set of steps to perform the desired task. However, in an agentic paradigm, we would want the flowchart to be automatically generated by the LLM, and the tools to be executed in the correct order so we can achieve similar outcome like the expert-curated flowchart. In order to proceed with the agentic paradigm, we need a LLM and the set of tools (numbered 1, 2 and 3 as in the figure above). The user should provide a query (or _prompt_) in natural language asking for the interaction network of BRCA1 gene. Our agentic system should first determine that the user query is a valid request (akin to the decision stage in the flowchart), and then figure out on it own that what tool should be called in what order to produce a result similar to what can be achieved through expert-curated flowchart. 


## The agentic workflow


<figure>
    <img src="/imgs/agents_llmflow.png"
         alt="The LLM flow.">
    <figcaption>A schematic of translating the mechanisms in flowchart through an agentic system comprising on an LLM and a set of available tools.
    </figcaption>
</figure>


The above picture is divided into three panels. The first panel (A) shows the expert-curated flowchart. There are four steps in the flowchart with the first one being a decision step. The other three steps involve tool calling and are associated with tools number 1, 2 and 3 that must be called in the same order. The middle panel (B) shows an agentic system where the boxed step in red, corresponds to the decision step in the traditional flowchart (the dashed arrow shows the correspondance). There is a _triage router_ in the middle that decides whether to proceed with an agent to do something further, or terminate the user request. If the _triage router_ doesn't terminate the user request, then it can call a _reponse agent_ to do something. It is the job of the _response agent_ to think and design the steps that correspond to the steps in the flowchart (dashed arrow shows the correspondance). Panel (C) shows the inner working of the response agent. The response agent _consults_ the LLM and decided to _pick_ the tool of relevance, executes it, and loops back to wait for the instructions from the LLM. Based on the instruction, it decides to either call a tool, or break the loop to terminate the process. If the system is designed properly, it should be able to call correct tools in correct order, similar to what we noted in the expert-driven flowchart.

### What it looks like when working
Let me show a demonstration of the agent and LLM interaction when provided with a user prompt. First start with a rubbish prompt and see the response. I have provided a _prompt_ in natural language as "Fetch network map for Mordor". Obviously, Mordor is not a gene name and the system's decision-making step at *triage_router* the input should fail. 

{% highlight python %}
response = overall_workflow.invoke({"messages" : ["Fetch network map for Mordor"]})
for m in response["messages"]:
    m.pretty_print()
{% endhighlight %}

```
The query 'Fetch network map for Mordor' does not contain any gene names based on the provided criteria. 
There are no words with all capital letters, words starting with 'Gene:', words containing 'ENSG' or 'ENSP', or alphanumeric combinations that fit the gene name definition. 
The term 'Mordor' is a fictional location from J.R.R. Tolkien's works and does not qualify as a gene name. 


Extracted Gene Id from the prompt = none

🔔🔔 The gene name could not be found. Call humans!
```
We see that the *triage_router* has flagged that Mordor is not a gene name. It also provides a logic as how it identifies a gene name. This is a logic that I had provided the system as an internal prompt (again using natural language) to the LLM.  The message further outputs an information *"The term 'Mordor' is a fictional location from J.R.R. Tolkien's works and does not qualify as a gene name."* - this is something that came out from LLM itself, and had no inputs from me while building the system.


Now, let's give a sensible prompt and see the response. This time, I am using a little hint for the system to identify the gene name from the prompt.

{% highlight python %}
response = overall_workflow.invoke({"messages" : ["Fetch network map for Gene:BRCA1"]})
for m in response["messages"]:
    m.pretty_print()
{% endhighlight %}

The following output shows *the chain of thoughts* process where first the *triage_router* approves the input and calls the agent. The agent goes in a loop with LLM and the set of available tools and calls them one after the other. The output contains blocks named as "Ai Message" and "Tool Message" that come each time the LLM is *thinking* and a tool is *called*. We see that there are three tool calls, each one after some *thinking* has been performed. These tools have been called in the same order as what we expected based on our expert-curated flowchart.

This is a basic demonstration of how a LLM combined with an agent can *stitch* a workflow using *the chain of thoughts*. This corresponds to the idea of *orchestrator* as we discussed in the beginning of this post. When the number of agents and tools increase, the complexity of the system will increase as well. I haven't shown in this example as how the system can have _memory_ and the ability to call _humans in the loop_ - the two capabilities that are central to any agentic system. But hopefully, you got a basic idea of about the fundamental capability an agentic system can bring. There are many frameworks for implementing an agentic system - I used LangGraph as the framework and Qwen as the LLM to build this demonstration. Now, an important question is - does it work consistently every time? The answer is - No! The LLMs can *behave* differently each time they are called, and thus, there are other engineering mechanisms that must be applied in form of *guardrails* - *humans-in-the-loop* being one of them.
